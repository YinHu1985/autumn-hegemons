# 架构与数据驱动设计

记录日期：2026 年 11 月 9 日；更新日期：2026 年 11 月 17 日。

用户明确要求从项目开始就采用文本数据驱动：游戏内容、数值和关系由 JSON 等文本文件定义，代码实现效果词条与通用规则。新增普通货物、建筑、科技或理念，应主要通过内容文件完成，避免修改多个耦合的系统。

用户已决定继续采用网页，并要求网页定义编辑器。当前已采用 TypeScript、React 和 Vite，实际实现见 [实施记录](implementation-notes.md)；Worker 等仍属目标架构。整体分层、目录、兵种与 modifier 接口及未决事项见 [网页架构规划](architecture-plan.md)。玩法规则见 [设计讨论记录](design-discussion.md)，预算、人力、建设及国家运行共识以 [首版结算与运行规则](core-rules.md) 为准，科研和理念见 [暂定科技设计](technology-design.md)。

## 内容与代码的边界

| 文本数据负责 | 代码负责 |
| --- | --- |
| 货物、特产、建筑、兵种、科技、理念、人才专长等内容目录 | 加载、校验、查询和引用这些内容的通用机制 |
| 国家基础资源、研究成本、成本档位、配方、产出、维护费、启发分组和贡献等参数 | 财政收入汇总、额度分配、科研推进、效果结算、战斗等计算规则 |
| 哪个对象拥有哪些效果，效果的对象、数值与条件 | 每一种效果或条件的准确含义、合法作用域和执行方法 |
| 事件触发条件、选项、奖励和后续事件 | 触发调度、条件判断、效果执行及防重复结算 |
| 剧本中的国家、省份、人物、军队与初始状态 | 新建游戏、命令处理、时间推进、AI 和存档管理 |
| 名称、说明、图标引用、显示分组和顺序 | 通用列表、面板和效果说明的生成与渲染 |

在已有机制范围内增加内容或调整组合，只改数据。新增尚不存在的机制，例如从零加入海战，需要扩展代码中的处理器；之后哪些兵种或科技使用它，继续由数据配置。复杂算法不强行搬成 JSON，也不在配置中嵌入任意 JavaScript。

## 内容注册表与稳定引用

所有内容使用稳定 ID 引用，显示名称与 ID 分开。建筑引用特产 ID，配方引用货物 ID，科技或理念引用效果与目标 ID；不用中文名称或数组下标作为关联键。

货物目录必须贯通整个游戏：生产配方、供需账目、相关界面和 AI 都查询内容注册表，而非在各处分别列出铁、铜、木材等固定集合。新增普通货物不应要求增加代码枚举、专用界面字段或逐货物结算分支。

特产与货物分开定义，例如牛是地方特产，皮革是作坊产出；粮食、鱼及稻粟变体可以引用同一个粮食财政产物和同一仓库类型。资源的记账方式与用途分别声明：粮食是可积累的主财政，人力具有征发与恢复规则，铜铁黄金等商品使用持续额度。编辑器、UI 和 AI 读取这些角色，不按显示名称猜测用途，也不把黄金当作默认货币。普通商品仍不启用库存。

军工作坊已选定产出二级军备商品额度，由兵种模板引用需求；不再保留直接增加指定兵种容量的生产分支。人力为唯一全国池，军团征募、补员和地方守备共用，池内储备与在役人数分开；征发、复员、失城和额度不足的规则由内核统一执行，不能借通用资源加减绕过 [已确认的记账语义](core-rules.md)。

运行时可以将 ID 编成内部索引以加快访问，但内容文件和存档关联仍使用稳定 ID。所有内容加载完毕后再解析跨文件引用，不能因文件先后顺序而漏掉引用。

JSON 在加载或明确重新加载内容时解析和校验，游戏推进时使用已经建立的注册表与索引，不逐日或逐帧重新读取、解析文本。

## 国家基础资源来源

用户已确认国家可以独立于地方经济直接提供资源，用于开局起步和平衡。国家本身就是合法来源，不要求虚构建筑、产地或首都；这是一类通用国家资源贡献，不是军备专用配额。内容可以引用任何已定义且支持相应记账方式的资源 ID，不在代码中固定铜、铁等名单。

财政粮食按每月收入入账，普通商品和二级军备按持续供给额度汇总。基础贡献独立于地方治理和建筑维护，不自动套用它们的产量折减；国家级加成是否影响基础贡献、具体影响哪些来源，须显式定义，范围与数值以后确定。人力若需要国家级贡献，应分别表达容量或恢复等已注册语义，不能将人数、容量、恢复率扁平化成普通商品产量。

建议采用带来源的资源贡献列表，或能表达同等语义的稳定资源 ID 到数量映射。下面仅示意国家内容中的配置，字段、通道名、资源 ID 和数值都不是最终 schema 或平衡参数：

```json
{
  "sourceType": "nation",
  "contributions": [
    { "resource": "base:goods/grain", "channel": "monthly_income", "amount": 100 },
    { "resource": "base:goods/copper", "channel": "supply_capacity", "amount": 10 },
    { "resource": "base:goods/leather_armor", "channel": "supply_capacity", "amount": 5 }
  ]
}
```

加载器校验资源引用与贡献通道是否相容。经济系统把国家来源和城镇、建筑等来源共同汇总，保留来源类型、持有国家和贡献明细；国家基础来源按国家计一次，不随城镇数量重复。财政、供需面板和 AI 使用同一最终结果，编辑器从资源目录选择引用并编辑贡献，不为基础军备再维护一套独立字段。

## 效果与条件注册

11 月 17 日确认将科技、理念、事件及未来政策统一到相同效果语法与入口：一次性动作负责即时状态变化，持续 modifier 具备名称、来源、目标、到期时间与可解释的数值词条，支持国家／城市范围和受限动态表达式。每个实例统一使用游戏内 `expiresAt`；永久效果的到期时间设在游戏时间窗口之外，不另开永久分支。来源撤销仍可提前移除，贡献明细由实际计算返回。完整约定见 [网页架构规划第 4 节](architecture-plan.md#4-按名称注册的-modifier-与行为接口)。已实施，当前配置格式和边界见 [统一效果配置](modifier-system.md)。

后续补充：科技、理念等常规贡献可从既有状态派生，额外 modifier 保存独立实例，两者共用计算和贡献明细。内政列表按来源提供默认显示规则，并允许单项覆盖；不显示在内政的科技／理念加成仍完整出现在具体数值反查中。科技等来源可配置一次性“添加 modifier”动作，在完成等触发时机立即创建额外实例，不因日后查询科技效果或读档而再次创建。纯一次性收益直接修改世界状态，不保存成 modifier。

建议建立效果、条件和数值属性的代码注册表。每种处理器声明所需参数、作用域、数值单位、叠加规则及说明方式。

例如，代码实现增加某类科研席位、改变建筑产出、提供研究进度或解锁某种能力；JSON 选择处理器并提供目标与数值。国家、省份、军团和部队之间的作用范围需要显式定义，不依靠隐含的全局继承。

持续数值 modifier 与一次性行为分开：持续效果记录来源，在科技掌握、理念实行、人物任职等对应阶段生效；一次性效果由明确事件执行。移除理念或调离人物时，可以准确撤销对应来源，不能只在获得时累加、撤销时猜测。

条件可组合“全部满足、任一满足、取反”等有限逻辑。具体条件调用已注册检查器，避免用任意对象路径修改状态，或逐个科技 ID 编写特殊判断。

效果文本应尽量从同一份结构化效果生成，例如自动显示“工造类科研席位 +1”，避免描述写一个数、实际结算另一个数。

## 数据形式示例

以下只是说明引用和效果表达，字段名、格式和数值都不是已定配置规范，也不为相应科技或建筑确定玩法效果。

一个产地建筑可以类似这样定义：

```json
{
  "id": "base:buildings/copper_works",
  "name": "铜冶作坊",
  "placement": {
    "type": "has_specialty",
    "specialty": "base:specialties/copper"
  },
  "production": {
    "outputs": { "base:goods/copper": 10 }
  },
  "monthlyUpkeep": { "base:goods/grain": 2 }
}
```

货物目录中另有 `base:goods/copper`，特产目录中另有 `base:specialties/copper`；`base:goods/grain` 的定义声明财政用途和余额记账。加工建筑可以用货物 ID 定义投入，普通商品由额度分配处理，财政费用由支付规则处理，不能不分角色地做同一种加减。以上字段和 ID 仍为示意。

理念实行效果的一条记录可以类似这样表达：

```json
{
  "type": "modifier",
  "scope": "country",
  "attribute": "research.parallel_limit",
  "selector": { "category": "craft" },
  "operation": "add",
  "value": 1
}
```

代码负责解释该属性和作用域；具体哪个理念使用、增加多少、成本多少，都由理念文件决定。理念的研究解锁与占槽实行效果分开，不因共用科研系统就自动在研究完成时施加所有理念效果。

## 校验与加载流程

候选流程为：读取内容清单 → 加载全部 JSON → 结构校验 → 解析引用与语义校验 → 建立只读注册表及索引 → 新建游戏或读取存档。

结构校验检查必填字段、类型、取值范围和已知字段；语义校验另查 ID 唯一、引用是否存在、效果作用域是否匹配、科技前置是否成环，以及理念是否错误配置了研究前置。配置错误应给出文件、条目 ID、字段位置和原因，尽可能一次报告全部错误，而非静默忽略或进入游戏后才失败。

JSON Schema 可以表达结构约束，验证器可考虑 Ajv；结构类型与校验规则应保持同一来源或自动同步，避免两份手写定义逐渐分叉。跨内容引用与图关系仍由专门的语义校验完成。[JSON Schema 官方说明](https://json-schema.org/learn/getting-started-step-by-step)、[Ajv 的 TypeScript 支持](https://ajv.js.org/guide/typescript.html)。

当前生产与军事科技有直系前置，理念只有三个成本档位且无研究前置。它们可以共用研究结构，但校验与生效阶段必须表达这一区别。

## 静态内容与运行状态

内容定义保存科技成本、建筑配方、兵种属性等；运行状态保存某国已掌握科技、在研进度、各类预算滑条与当前周期实际维护状态、某城施工进度、某军团当前人数等。界面状态保存当前选择、展开面板和镜头位置。

本月收入依据既定运行状态，月底各类独立维护比例在财力不足时同比缩减，实付决定下月状态。预算意图与当前有效状态必须分开保存，不能读档后按新滑条重算旧周期；每城单项建筑施工、人才招募计时及事件期限也属于内核运行状态。具体规则和仍待补齐的新增对象、失效出口见 [首版运行规则](core-rules.md)，不另建第二套编辑器规则。

三者分开。不能将完整定义复制进每个国家后各自修改；可用产能、modifier 汇总和界面说明等派生结果应能从定义与运行状态重建。规则、AI、事件和界面校验共用内核提供的查询与命令，不分别解释内容数据。

内容可以按类别拆文件，也可以按单个条目拆文件，由清单列出加载路径；不必维护一个巨大的 JSON。目录候选包括货物、特产、建筑、科研、兵种、事件、剧本、平衡参数及本地化文本，具体组织后定。

## 修改生效与内容版本

可修改内容建议作为运行时读取的独立文件，而非全部编译进 JavaScript 包。开发时修改 JSON 后重新加载内容或重开游戏即可验证，无需修改规则代码；生产发布时也需更新实际提供给游戏的内容文件并处理缓存。Vite 的 public 目录可原样提供和复制独立文件，是候选实现方式之一。[Vite 静态资源说明](https://vite.dev/guide/assets#the-public-directory)。

游戏运行途中热更新另行设计，不能承诺任意修改在研成本、货物列表或现存军队定义后立即兼容。首版可先采用重新加载内容并新建游戏的验证流程，不兼容旧格式存档，格式不符明确拒绝加载。

建议保存内容格式版本、内容包标识和版本或指纹。删除、改名 ID 或改变规则语义时，按当前格式重新开局，不能静默丢失内容或套用旧规则。若以后支持模组，候选先采用明确加载顺序、按 ID 整项替换与冲突报告；复杂的深层补丁合并暂不预设。

## 网页与桌面的选择

用户已确认当前继续采用 Web。建议使用独立 TypeScript 模拟内核，运行时加载内容并校验；模拟内核可放在 Worker 中。具体库和宿主实现仍属于架构规划，数据驱动不要求改用 Rust 或原生界面。

浏览器可以加载站点提供的 JSON，也可以通过导入入口读取用户选择的内容文件。它不能未经用户授权任意扫描电脑上的游戏或模组目录；文件访问方式与浏览器支持情况需要单独适配。[MDN File System API](https://developer.mozilla.org/en-US/docs/Web/API/File_System_API)。

如果交付目标是玩家直接编辑安装目录或模组目录后重启生效，桌面文件适配更自然。可以保留 Web 界面并采用桌面壳，内容依旧保留为外部文件；这与模拟内核是否使用 Rust 是两项决定。

## 定义编辑器

用户补充要求网页提供编辑各类内容定义的界面，并已选择继续采用网页。编辑器纳入顶层架构；以下界面范围与保存方式是实施建议，尚未选定库或开始实现。

网页开发期间也可以直接修改项目中的 JSON，再通过重新加载验证；编辑界面是另一种编辑同一份内容的入口。即使以后转为桌面交付，该界面也可以继续使用。

首版建议采用类别列表、搜索和条目表单，支持新增、复制、修改、删除，以及 JSON 原文查看和编辑。基础字段按结构定义生成；建筑配方、科技前置、效果参数等增加适合游戏内容的控件。例如配方选择货物后填写额度，效果选择已注册词条后填写目标和数值，引用下拉框从当前内容目录生成，而非另写一份固定选项。

编辑器与游戏加载器共用结构定义、效果参数定义和完整校验流程。字段分组、中文标签、控件布局可以另外提供显示元数据，但不能重新实现一套合法性规则。基于 JSON Schema 生成表单已有现成方案；游戏中的引用选择器、效果编辑和配方展示仍需适配。JSON Forms 可作为候选参考，不代表已决定采用。[JSON Forms 官方说明](https://jsonforms.io/docs/)。

表单与原文编辑同一份内容草稿，切换或保存时不得静默丢失合法字段。草稿可保留未完成的修改；加载为可运行内容之前必须通过整体校验，包括跨条目的引用。删除条目或修改稳定 ID 时应展示引用影响，避免只检验当前表单。编辑定义与修改某局存档分开，首版建议校验后用新局试玩，运行中热更新沿用前述待定边界。

保存需要区分运行环境，界面编辑并不等于已改写项目文件：

| 环境 | 候选保存方式 |
| --- | --- |
| 本地开发网页 | 开发工具提供限定内容目录的读写接口，编辑器保存回项目 JSON；也保留直接编辑文件的方式 |
| 纯静态网页 | 导入、导出 JSON 内容包；可另存浏览器草稿，但明确提示草稿尚未导出，不会自动改写站点原文件 |
| 支持本地文件访问的浏览器 | 用户选择并授权目录后读写内容文件；保留导入导出作为兼容方案 |
| 桌面应用 | 通过桌面文件适配层读写内容目录，复用编辑界面与校验器 |

浏览器文件与目录读写依赖用户授权和具体浏览器支持。[MDN File System API](https://developer.mozilla.org/en-US/docs/Web/API/File_System_API)。编辑器先做好列表、表单、引用选择、校验与保存闭环；科技树拖拽排版、事件流程图、批量平衡工具等可以后续增加，不计入首版基本编辑能力的工作量估计。

## 首批验收场景

- 只添加 JSON 和素材，就能新增一种普通货物、一个产地或加工作坊，以及引用它们的科技；生产、额度面板、效果说明和 AI 对该内容的基本使用无需新增 ID 分支。
- 只改国家内容，就能为已有或新增资源配置基础贡献；无需建筑、产地或首都，财政粮食进入月收入，商品和军备进入持续额度，明细、UI、AI 与编辑器均识别国家来源。地方治理或建筑低维护不意外削减该贡献，也不因多城或读档重复计入。
- 只修改数据，就能调整科技工作量、建筑投入产出或效果数值，界面说明与实际结算一致。
- 理念使用研究系统解锁，实行效果受槽位控制，并且不因历史关系意外出现研究前置。
- 删除被引用的货物、拼错效果名、配置错误作用域或产生科技前置环时，加载校验给出明确错误。
- 同一套内容与种子可以在无界面模拟中验证，界面不会维护另一套经济或科研规则。
- 预算计划与当前实际维护分开，存读档不改变周期归属；全国两人力池、军备额度和每城施工约束通过同一内核校验，已确认的软限制不被统一写成硬拒绝。
- 网页定义编辑器与手写 JSON 可以往返编辑同一份内容；引用选择随目录变化更新，导出再导入保持语义一致，加载校验与游戏使用同一套规则。

这些是拟用于实现验收的标准，当前尚未编写程序或运行相应验证。
